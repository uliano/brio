# ILI9481 (a 320x480 panel controller)

Documents of record: the ILI9481 data sheet version 0.27 - chapter 7 for
the interfaces, chapter 8 for the commands, 13.3.2 for the serial
clock's limits - and THE BENCH, which is the authority wherever the two
differ. Traits: `devices/ili9481.hpp`; the vocabulary it is written in is
`devices/dcs.hpp` ([dcs.md](dcs.md)). Simulator:
`brio/host/sim_dcs_panel.hpp`, whose conformance suite is
`test/test_ili9481` (host, no hardware). The bench findings below were
taken on one 3.5" module driven over a four-wire serial interface.

## What the silicon does

**320 columns by 480 pages, eighteen bits a pixel on this link and no
other.** The four-wire serial interface stores three bytes a pixel with
each channel in the six most significant bits of its byte and the low
two ignored on a write (7.2); COLMOD comes up at 0x66 and RDDCOLMOD
answers 0x66 on a module that has only been woken. MADCTL comes up at
0x00.

**The three walk bits reorder the counter INSIDE the window and never
move its origin.** This is the finding that shapes every driver above
the part, and it is not what the command's name suggests. Under B6
(column order) the logical origin of a window of columns 0..3 and pages
0..1 is physical (3,0) and not (319,0); under B7 (page order) it is
(0,1). Under B5 (exchange) the two axes swap ROLES: CASET then addresses
the PAGES (0..479) and PASET the COLUMNS (0..319), and the counter steps
the pages first. B6 still reverses the column direction and B7 the page
direction, whichever of the two each has become - so the eight codes are
the eight corners and directions of one rectangle, and a read under a
code finds exactly what a write under the same code put there. The
registers keep the bytes they were given and the axes are resolved when
the counter walks: a MADCTL written AFTER the window decides which axis
is which (a window written as columns 104..107 and pages 202..203 under
0x00, then B5, then eight pixels, lands at column 202 and pages
104..107, the pages stepped first).

**The BGR bit acts on writes alone.** A pixel written with B3 set is
stored with its first and third byte exchanged, and read back AS STORED.
So a program cannot use that bit to fix a module's colour order and
still have its read-back come out in its own order; a driver that wants
an oracle writes the bytes in the order the module needs and leaves the
bit clear.

**The serial read path has three framings, not one.** 7.2.2 gives every
read command a "dummy read" as its first parameter and its figures do
not say whether that is a byte or a clock. Measured, it is neither one
answer nor the same answer:

- a MULTI-PARAMETER register read comes one dummy CLOCK late - the whole
  stream shifted right by one bit. The device code (BFh) answers
  02 04 94 81, which reaches a host as the raw bytes 01 02 4A 40 FF;
- a SINGLE-parameter read (RDDPM 0Ah, RDDMADCTL 0Bh, RDDCOLMOD 0Ch) has
  no dummy at all: the value is the first byte clocked;
- RAMRD (2Eh) and read memory continue (3Eh) begin with ONE DUMMY BYTE,
  which reads 0x80, and then three bytes a pixel.

**The read pointer counts the bytes CLOCKED, not the pixels delivered.**
A read memory continue starts at the first pixel not fully clocked, from
that pixel's first byte - so a pixel cut short by spare clocks is read
again whole. Clock exactly what you need.

**The address counter is an ADDRESS, and only RAMWR and RAMRD move it.**
RAMWR puts the write address at the walk's first pixel and RAMRD the read
address; a window re-issued - CASET and PASET together, or either alone,
with the same values or others - leaves both where they were, and the
two are independent of each other (a RAMWR between two reads moves the
read address not at all, and a RAMRD between two writes not the write
address). It is an address and not an index: with the write address at
the third pixel of a window, a window one column to the right takes the
next write memory continue at the SAME column, and a window moved far
away takes nothing - the pixel lands nowhere. Along the walk the counter
WRAPS: a write past the window's last pixel lands on its first again
(twelve pixels into a window of eight leave tags 8..11 on the first four
cells), and so does a read.

**A pixel cut short at the close of a write is DROPPED.** A RAMWR that
ends one byte into a pixel and a write memory continue that brings the
rest leave the memory holding the continuation's first three bytes as a
pixel, from its own first byte: the byte left over is gone and the
address has not moved for it.

**Windows the axes cannot hold are two different cases.** A CASET or
PASET whose START is beyond the axis it addresses (400 on the columns,
500 on the pages) is IGNORED whole: the register keeps its values and a
following write lands in the window that stood before. One whose END is
beyond the axis (316..323) or that runs BACKWARDS (210..205, 105..103)
is TAKEN, and the window is no window: a write lands nowhere in the
frame, and a read answers 0xA8 on every byte clocked - an odd page's
reset fill, as if the address had left the array; the value is measured,
the reason is not known.

**RDDPM's bits.** Bit 4 sleep out, bit 3 normal mode, bit 2 display on,
and D7 reads 0 as the bit table says ("set to 0"), whatever the prose
under it says about the booster: 0x1C after SLPOUT and DISPON.

**The clock's two ceilings.** 13.3.2 gives 40 ns high plus 40 ns low for
a write (12.5 MHz) and 120 plus 120 for a read (4.17 MHz).

**Two facts of the MODULE, not of the controller**, stated here because
a simulator has to answer with the bytes the bench saw: RDDID (04h) and
RDDST (09h) read all ones - the link's pull-up, not a value, so the
controller's multi-parameter framing has no stream to shift there; and a
hardware reset leaves the frame memory in alternate pages of 0x54 and
0xA8, the even pages 0x54.

**INVON changes nothing in the memory** - it is a display bit, and a
read-back is unaffected by it.

## Types and verbs

One type, `Ili9481`, with a deleted constructor: it is a bag of
constexpr facts and never an object. There is no verb here but one
classifier.

The frame memory:

| Name | What it says |
|------|--------------|
| `columns`, `pages` | 320 and 480, the native array |
| `bytes_per_pixel` | 3 - this link stores eighteen bits and no other width |
| `reset_colmod` | 0x66, and the only code the serial interface can use |
| `reset_madctl` | 0x00 |
| `reset_fill_even_page`, `reset_fill_odd_page` | 0x54 and 0xA8, what a hardware reset leaves |

The read path:

| Name | What it says |
|------|--------------|
| `read_framing(command)` | the framing of one command, as `DcsReadFraming`: a dummy byte for the two memory reads, aligned for the three single-parameter registers, a dummy clock for the device code, undriven for everything else - the two identification registers among them, because this module drives neither |
| `memory_read_dummy_byte` | 0x80, what that dummy byte reads |
| `device_code_command`, `device_code` | 0xBF and the four bytes 02 04 94 81 |
| `module_rddid_all_ones`, `module_rddst_all_ones` | the module's silence, marked as the module's |

The clock, in two groups that are deliberately not one:

| Name | What it says |
|------|--------------|
| `write_clock_max_hz`, `read_clock_max_hz` | 13.3.2's ceilings, 12.5 MHz and 4.166 MHz |
| `measured_write_exact_hz`, `measured_write_wrong_hz` | 12 MHz and 24 MHz |
| `measured_read_exact_hz`, `measured_read_wrong_hz` | 12 MHz and 24 MHz |

The wake, as times and not as code - a driver owns the waiting:
`reset_low_ms` 10, `reset_settle_ms` 150, `sleep_out_ms` 150,
`display_on_ms` 25.

## How to use it

The wake a driver performs, with the numbers taken from the traits
rather than written twice:

```cpp
using C = brio::Ili9481;
reset_pin.clear();  wait_ms(C::reset_low_ms);
reset_pin.set();    wait_ms(C::reset_settle_ms);
link.command(brio::Dcs::slpout);   wait_ms(C::sleep_out_ms);
link.command(brio::Dcs::dispon);   wait_ms(C::display_on_ms);
link.command(brio::Dcs::invon);    // this module needs it
```

Clocking a register read, with the framing asked of the controller
rather than assumed:

```cpp
constexpr auto framing = brio::Ili9481::read_framing(brio::Dcs::rddpm);
static_assert(framing == brio::DcsReadFraming::aligned);   // no dummy at all
uint8_t raw[2];
link.read(brio::Dcs::rddpm, raw);
const uint8_t power_mode = raw[0];
```

A memory read, clocked to the byte, so that a following read memory
continue resumes on a pixel boundary:

```cpp
uint8_t raw[1 + pixels * 3];                     // the dummy byte, then the pixels
link.read(brio::Dcs::ramrd, raw);
CHECK(raw[0] == brio::Ili9481::memory_read_dummy_byte);
```

The panel simulated, with the module's own glass, as a suite drives it:

```cpp
brio::SimDcsPanel<brio::Ili9481> panel{{.column_mirror = true, .wants_inversion = true}};
brio::SimDcsSerial<decltype(panel)> link{panel};
link.select(true);
link.dc(false);  (void)link.byte(brio::Dcs::ramrd);
link.dc(true);   const uint8_t dummy = link.byte(0xFF);   // 0x80
```

## Bench findings

From a probe over a four-wire serial interface at 6 MHz for writes and
3 MHz for reads unless another rate is named:

- **The controller answers on its data-out line.** The device code
  (BFh) reads 02 04 94 81 behind ONE DUMMY CLOCK - so the data sheet's
  "dummy read" is a clock and not a byte for that command. RDDPM 0x1C,
  RDDMADCTL 0x00 and RDDCOLMOD 0x66 arrive BYTE-ALIGNED with no dummy at
  all; RDDID and RDDST read all ones on this module.
- **The frame memory read is one dummy byte, which reads 0x80, and then
  three bytes a pixel**, the six most significant bits of each the
  colour and the low two zero - a different alignment from the device
  code's. Read memory continue has its own dummy byte and picks up at
  the pixel after the last one fully clocked; a pixel cut short by spare
  clocks is read again from its first byte.
- **The whole frame (460800 bytes) reads back byte for byte as
  written**, under a pattern whose every byte moves with the pixel's
  position, so a stream one byte out of step disagrees at once.
- **Rates.** A write at 12 MHz - the data sheet's ceiling - reads back
  exact; 24 and 48 MHz leave garbage. A READ is exact at 6 and at 12
  MHz, three times the data sheet's 4.17 MHz, and wrong at 24. One
  module, one desk: printed, and a driver's defaults stay inside the
  data sheet.
- **The eight scan orders, each written and read back**, with the
  physical home of the first, second and fifth pixel of a window four
  wide and two high at the origin:

  | MADCTL | logical (0,0) | (1,0) | (0,1) |
  |--------|---------------|-------|-------|
  | 00 | (0,0) | (1,0) | (0,1) |
  | 40 | (3,0) | (2,0) | (3,1) |
  | 80 | (0,1) | (1,1) | (0,0) |
  | C0 | (3,1) | (2,1) | (3,0) |
  | 20 | (0,0) | (0,1) | (1,0) |
  | 60 | (1,0) | (1,1) | (0,0) |
  | A0 | (0,3) | (0,2) | (1,3) |
  | E0 | (1,3) | (1,2) | (0,3) |

  The write's mapping and the read's agree under all eight, which is
  what makes a read-back an oracle in every orientation. Under 08 the
  read finds the pixel where 00 does and the write stored it with its
  first and third byte exchanged.
- **The window's edges and the two addresses.** Twelve pixels into a
  window of eight (columns 104..107, pages 202..203 under 00): the ninth
  lands on the window's first cell, the first four cells hold the last
  four pixels; a read of twelve from the same window answers the first
  four again after the eighth. The window re-issued after two pixels,
  or CASET alone, or PASET alone, and then a write memory continue: the
  pixel lands on the third cell. A window one column to the right after
  two pixels: the continue lands at column 106, the address. A window
  far away: three pixels land nowhere. A RAMRD of two, the window
  re-issued, a read memory continue of one: pixel 2. A RAMRD of two, a
  RAMWR of one, a continue of one: pixel 2 still. A RAMWR of one, a
  RAMRD of three, a write continue of one: the second cell.
- **A pixel cut short.** A RAMWR of four bytes into a window of three
  (one pixel and the first byte of the next) and a write memory
  continue of five (the other two bytes and a whole pixel): the second
  cell holds the continue's first three bytes and the third cell is
  untouched.
- **Windows the axes cannot hold**, each after a sentinel window of
  four cells at column 8 of page 106, one pixel written after the
  command: CASET 400..403 - the pixel in the sentinel, the command
  ignored; CASET 316..323 - nowhere; CASET 210..205 - nowhere, and a
  RAMRD of two from it answers A8 A8 A8 | A8 A8 A8; CASET 304..307 then
  PASET 500..501 - the pixel at column 304 of page 106, the PASET
  ignored and the page window before it standing; CASET 304..307 then
  PASET 105..103 - nowhere.
- **MADCTL after the window.** CASET 104..107 and PASET 202..203 under
  00, then 20, then eight pixels: the first at column 202 of page 104,
  the second at column 202 of page 105 - CASET's bytes became the pages
  and the walk steps them first.
- **Where a window lands once B5 has exchanged the axes.** Under 20, a
  CASET of 340..343 with a PASET of 150 lands at pages 340..343 of
  column 150, and a full run (CASET 0..479, PASET 40) reaches page 479
  with or without B6. Under 00 a CASET of 200..203 with a PASET of 300
  lands at columns 200..203 of page 300, under 40 a CASET of 100..103
  with a PASET of 340 at columns 100..103 of page 340, and under A0 a
  CASET of 300..303 with a PASET of 170 at column 170 of pages 300..303.
  A PASET PAST 319 UNDER B5 names columns that are not there, which is
  a start beyond the axis: the command is ignored and the window before
  it stands.
- **Two facts of the module, seen on the glass and not in the frame
  memory:** it shows MEMORY COLUMN 319 AT ITS LEFT, so a picture drawn
  under MADCTL 00 is mirrored, and it is wired with its colour channels
  crossed. Of the display bits, B1 (horizontal flip) and B4 (line
  address order) DO NOTHING here and B0 (vertical flip) mirrors the
  glass top to bottom - so the module's own mirror cannot be undone by
  B1 and belongs in the driver's rotation map. The panel needs INVON or
  every colour is its complement, with the memory unaffected.
- **A reflash fills the frame memory with 0x54 and 0xA8 in alternate
  pages**, the even pages 0x54: a census taken after flashing another
  program therefore describes the reset and not the program, which is
  why a program verifies its own writes in the same run.

## Not covered yet

Driver gaps:

- **The panel driver itself** - the rotation map, the surface shapes,
  the oracle verb in logical coordinates. Only the traits are here,
  because the driver stands on the link concept [dcs.md](dcs.md)'s own
  gap list is waiting for; it is the next step of the command tier.
- **Everything of chapter 8 that is not a DCS command**: the power
  control registers, the gamma curves, the frame rate and inversion
  control, the panel driving setup. The module comes up usable without
  any of them and no measurement here needed one - born with the first
  program that has a reason to move one.
- **The tearing effect line** (TEON/TEOFF). Declined until a driver
  streams a frame it cannot afford to tear: the module's connector
  carries the signal, but nothing here has a frame rate to synchronize
  to.
- **The 8080 parallel and the 16-bit serial interfaces** of chapter 7.
  Declined: the module wires four wires, and an interface with no board
  behind it would be a framing nobody could measure.
- **The other read registers** the vocabulary names (RDDIM 0Dh, RDDSM
  0Eh, RDDSDR 0Fh). Their framing is presumed to be the other
  single-parameter reads' and the bench clocked none of them; the
  simulator therefore answers them as unknown.

Implemented, not bench-verified:

- **`write_clock_max_hz` and `read_clock_max_hz` as ceilings a driver
  obeys.** The numbers are the data sheet's and the bench measured
  around them in both directions, but nothing in code refuses a rate
  above them today - a driver with a link is what would, and it is that
  driver's suite that would measure the refusal.
- **The wake constants as one sequence.** Each was proved on the bench
  as part of a working wake; what is not measured is which of the four
  waits can be shortened, because the probe never tried to shorten one.
