# SHA-256 accelerator (RP2350)

Documents of record: the RP2350 datasheet (build d126e9e), 12.13 (the
accelerator: 12.13.1 the message padding the standard defines and this
block does not do, 12.13.2 the throughput, 12.13.3 the data widths and
the byte swap, 12.13.4 the data request, 12.13.5 the registers), 2.1.3
(the atomic register aliases, and why none of them touches this block's
one control register), 5.4.4 (the bootrom's own use of the block and the
boot lock that arbitrates it), 7.5 (the reset controller); FIPS PUB 180-4
for the function itself. No item of Appendix E is filed against this
block. The driver: `brio/rp2350/sha256.hpp` over `brio/util/sha256.hpp`,
which is the same function in constexpr C++ and is what the silicon is
judged against; that half is host-tested in `test/test_sha256` against
the standard's published vectors. The reference suite:
`test_rp2350_blocks`, letters b, c and d, which runs on both of this
chip's architectures from one source.

## What the silicon does

THE COMPRESSION FUNCTION IN HARDWARE, AND NOTHING ELSE. Ten registers: a
control and status word, a write-only data port, and eight read-only
result words. A write to CSR.START loads the eight initial state words -
the fractional parts of the square roots of the first eight primes - and
clears the internal counters. Every sixteen words written to WDATA are
one 512-bit block, digested into the state; SUM0..SUM7 hold the state
after the last block that completed. There is no message length
register, no context to save and restore, and no second instance.

**The padding is software's** (12.13.1). The standard's trailing one bit,
the run of zeros and the 64-bit message length in bits are bytes like any
others here, and a caller owes them. That arithmetic is written once in
`util/sha256.hpp` and shared by the software path and this driver, so the
two cannot disagree about where a message ends.

**BSWAP, and why a word is loaded little-endian** (12.13.3). The bus
interface assembles byte and halfword writes into a message word in
LITTLE-endian order, so that the same buffer transferred by DMA at any
width gives the same answer on a little-endian machine. SHA-256 wants the
first byte of the message in the MOST significant lane of its word.
CSR.BSWAP, SET AT RESET, swaps the assembled word on its way into the
core and reconciles the two. The driver leaves it set and loads each word
of the message little-endian, which makes a word write and four byte
writes the same operation - and makes the driver independent of the
machine's own endianness. With BSWAP clear the same SIXTEEN WORDS digest
as the block with every four bytes reversed - measured, at the block,
because at the message they do not: `hash()` builds the padding as bytes
too, so a message hashed with BSWAP clear has its padding reversed along
with its text and its digest is that of no message at all.

**Mixing widths inside a block loses data** (12.13.3). The interface
accumulates 8- and 16-bit writes in a 32-bit shift register; taking that
register from below 32 bits to above in one write "silently drops data".
The rule the chapter gives is not to mix widths within one 64-byte block;
this driver writes whole words only and never faces it.

**The handshake, and the flag that catches a missed one.** After sixteen
words the core is busy for 57 cycles: CSR.WDATA_RDY goes low, and a write
during that window is dropped with CSR.ERR_WDATA_NOT_RDY left standing to
say so. Every write here polls first, and the error flag is a first-class
verb, because a suite that does not read it cannot tell a lost word from
a wrong answer.

**CSR carries four kinds of bit in one word**, which is why no atomic
alias of 2.1.3 touches it: two ordinary read-write fields (BSWAP,
DMA_SIZE), one self-clearing bit (START), one write-one-to-clear flag
(ERR_WDATA_NOT_RDY) and two read-only statuses. The set alias ORs a bit
into the register's contents, which would SET the write-one-to-clear flag
rather than clear it; and a plain read-modify-write would carry a
standing error flag back as a one and clear it in silence. Every store in
this driver is therefore the two configuration fields as they read, plus
the one action bit being asked for.

**SUM_VLD is high immediately after START.** A digest taken before any
data is written is the initial state and not a message's - which is why
`hash()` always writes at least the padding block, and why the suite
measures the initial state on purpose.

**Throughput** (12.13.2). Sixty-four system clock cycles to write a block
over the APB (four cycles a word) plus 57 to digest it: one block per 121
cycles at best, 0.53 bytes a cycle, 79.3 MB/s at 150 MHz. That figure is
the DMA's; a polled loop pays a status read per word on top of it.

**One sum at a time.** There is one block and no context save, so two
owners cannot interleave messages through it. 5.4.4 says the same of the
bootrom's own use and offers boot lock 0 as the mechanism for agreeing
about it; brio's programs have one owner, so this driver states the rule
and enforces nothing.

**The DMA request is for a WHOLE BLOCK** (12.13.4). There is no FIFO -
data goes straight into the message schedule - so CSR.DMA_SIZE must match
the channel's transfer width before the channel is triggered, and a
transfer must start on a block boundary and run a multiple of sixteen
words.

## Types and verbs

In `brio/util/sha256.hpp`, target-free and constexpr:

- `Sha256Digest` - the eight state words H0..H7, with `bytes()` for the
  canonical serialization (each word most significant byte first) and an
  equality comparison.
- `sha256(span)` - the whole function over a byte range, padding
  included. Answers at compile time for a constant.
- `sha256_compress(state, block)` - one 512-bit block into a running
  state, for a caller that owns the loop.
- `sha256_tail(leftover, total_bytes, out)` - the padding as a run of
  bytes ending on a block boundary: 64 or 128 and never anything else.
  The half of the job the hardware does not do.
- `sha256_initial_state`, `sha256_round_constants`, `sha256_block_bytes`,
  `sha256_digest_bytes`, `sha256_max_tail_bytes`.

In `brio/rp2350/sha256.hpp`:

- `Sha256::init()` - the block cycled through its subsystem reset, BSWAP
  set, DMA_SIZE at words, the error flag cleared, the state machine
  started. `release()` puts the block back into reset, which is the only
  way to make its state unreadable.
- `Sha256::hash(message)` - the whole function in hardware: start, the
  message's whole blocks, the software padding, the digest. Nothing when
  the core stopped answering, with `last_error()` saying which way
  (`Sha256Error::not_ready`, `no_sum`, `write_lost`).
- The lower verbs, for a caller feeding the block from somewhere else:
  `start()`, `write_word()` (with the handshake), `write_word_unchecked()`,
  `write_block()` (64 bytes, loaded little-endian), `digest()`.
- The status: `wdata_ready()`, `sum_valid()`, `write_error()`,
  `clear_write_error()`.
- The configuration: `byte_swap()` both ways, `dma_size()` over
  `Sha256DmaSize::bytes|halfwords|words`, and the constants
  `Sha256::dreq` (the pacing request a channel names) and
  `Sha256::reset_block`.

## How to use it

```cpp
brio::Sha256::init();

// the whole message, padding included
if (auto d = brio::Sha256::hash(bytes)) {
    if (*d == brio::sha256(bytes)) { /* the silicon agrees with the definition */ }
}

// or feed it a block at a time, and pad by hand
brio::Sha256::start();
for (auto block : blocks) { brio::Sha256::write_block(block); }
std::array<uint8_t, brio::sha256_max_tail_bytes> tail{};
const size_t n = brio::sha256_tail(leftover, total_bytes, tail);
for (size_t i = 0; i < n; i += 64) {
    brio::Sha256::write_block(std::span{tail}.subspan(i, 64));
}
const auto digest = brio::Sha256::digest();
```

The software twin alone, on any target and at compile time:

```cpp
constexpr auto known = brio::sha256(std::span<const uint8_t>{message});
```

## Bench findings

On an RP2350 in the QFN-80 package, **stepping A2**, clk_sys at 150 MHz,
on BOTH architectures: `test_rp2350_blocks` reports **71 pass, 0 fail**
on the Cortex-M33 pair and on the Hazard3 pair, from one source, each on
three flash-and-run cycles. Every verdict of this chapter reads the same
on the two halves; where a number differs, both are given.

- **SUM0..SUM7 PRESENT THE STATE AS WORDS H0..H7**, which 12.13 does not
  say. The letter compares the eight registers with the constexpr twin's
  digest both directly and after a byte swap per word: the direct
  comparison holds and the swapped one does not. So `digest()` reads them
  straight, and `Sha256Digest::bytes()` is where the big-endian byte
  order of the standard's output is applied.
- **THE THREE PUBLISHED VECTORS AGREE**, the empty message, `abc` (FIPS
  180-4 B.1) and the 56-byte message of B.2 whose padding lands in a
  second block - the case the tail arithmetic exists for. So does the
  digest of 4 kB, against the same twin.
- **WHAT THE POLLED PATH COSTS.** 4096 bytes through `hash()`:
  **296 to 298 us on the Cortex-M33 half (13.7 to 13.8 MB/s, 10.83 to
  10.91 clk_sys cycles a byte) and 265 to 267 us on the Hazard3 one
  (15.3 to 15.5 MB/s, 9.70 to 9.77 cycles a byte)** - the RISC-V half the
  faster of the two, by some eleven per cent, on identical C++. The
  software twin on the same bytes takes 2547 to 2548 us and 2216 to
  2217 us, so the accelerator is **eight and a half times** the twin on
  the Cortex-M33 half and **eight and a third** on the Hazard3 one.
  12.13's own floor is 64 words of four cycles plus 57 to digest - 121
  cycles a block, 1.89 cycles a byte - so **the polled feed loop and not
  the engine is what this measures**. It moves with where that loop lands
  in the XIP cache: the same source with one letter's code added ahead of
  it measured 7.25 cycles a byte in one arrangement and 10.83 in another,
  each stable to a hundredth of a cycle across three flash-and-run
  cycles. The number is a property of the image, not of the block.
- **A WORD WRITTEN INTO THE BUSY CORE IS DROPPED AND SAYS SO.** Sixteen
  words fill a block, the core goes busy, and a seventeenth written with
  no handshake raises ERR_WDATA_NOT_RDY - which is what makes the polled
  handshake necessary and checkable. The flag is write-one-to-clear.
- **A DIGEST TAKEN AFTER START WITH NOTHING WRITTEN IS THE INITIAL
  STATE**: SUM0 reads 0x6A09E667, the first of the eight fractional square
  roots. That is why `hash()` always writes at least the padding block.
- **BSWAP, SETTLED AT THE BLOCK AND NOT AT THE MESSAGE.** Sixteen words
  written by hand with no padding after them: with BSWAP set the digest is
  the definition's compression of the buffer read big-endian, with BSWAP
  clear it is the compression of the same buffer with every four bytes
  reversed, and the two differ. The question has to be asked at the block
  because `hash()` builds the padding AS BYTES - with BSWAP clear the
  padding words enter reversed too, so the whole-message result is the
  digest of no message at all. `init()` sets BSWAP and no verb here leaves
  it clear.
- **The DMA request is 54**, the number 12.6.4.1's table gives, and
  DMA_SIZE is left at words.

## Not covered yet

Driver gaps, each with its reason:

- **A DMA engine.** The block raises `Dreq::sha256` and `dma_size()` is
  here, but no engine type is: a channel that feeds this block is the
  caller's, and what would make it a `BlockPlayer` (util/block_stream.hpp)
  is accounting no program here has asked for. Born with the first
  program that hashes something it does not already hold in memory.
- **Byte and halfword writes to WDATA.** The port takes them, and a DMA
  from an unaligned buffer needs them; this driver writes whole words
  only, which is the fastest form and the one with no width-mixing trap.
  Born with the engine above.
- **The boot lock** (5.4.4's LOCK_SHA_256): the ROM checks it only when
  boot lock 7 has been claimed, and nothing here claims either. Born with
  the first program that calls a ROM function which uses this block.
- **HMAC, key derivation and signature checking.** They are built on this
  and nothing in brio needs them.

Implemented but not bench-verified, each with what would measure it:

- **`release()` putting the block back into reset.** `init()` cycling it
  through RESETS is exercised by every letter above - nothing would
  answer otherwise - but the release side is called by no letter, because
  a suite that released the block would have to re-init it before the
  next one. A letter that released it and read RESET_DONE back would
  close this.
- **`write_block()` refusing a span that is not a whole 64-byte block.**
  The guard is there and returns `false`; no letter passes it a short
  span, since `hash()` is what every letter uses. One line in a letter
  would close it.
